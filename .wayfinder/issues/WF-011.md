# Characterize undocumented timer mutations in a live account

## Question

Using a controlled FreshBooks project and authenticated development CLI, what observable request, response, and cross-client behavior occurs for pause, resume, correcting a running duration, multiple simultaneous unlogged timers, stale writes, logging failures, remote edits, and crossing local midnight?

## Blocked by

- None

## Progress

[FreshBooks live timer characterization](../../docs/research/live-timer-characterization.md) records the sanitized, cleaned-up observations for timer segmentation, pause/resume state, Duration Correction, consolidation/rounding on log, stale writes, and public Time Entry endpoint limitations. The web UI's two-request timer start shape is now captured: a blank unlogged Time Entry POST with `timer: {}` creates the timer identity, then a PUT assigns the selected project, service, identity, and note. Pause closes the open segment with elapsed whole seconds. Resume appends a new open segment carrying the timer identity. A running Duration Correction preserves closed durations while rebasing the open segment to the requested aggregate. Logging preflights the project, then PUTs the timer resource with its Time Entry segments. A controlled CLI lifecycle validated all five mutations and identity continuity, then verified complete cleanup. The different identity in the browser log capture came from a user-confirmed restart after the earlier timer hit an unrelated web UI save error.
