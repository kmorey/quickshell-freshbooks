# Characterize undocumented timer mutations in a live account

## Question

Using a controlled FreshBooks project and authenticated development CLI, what observable request, response, and cross-client behavior occurs for pause, resume, correcting a running duration, multiple simultaneous unlogged timers, stale writes, logging failures, remote edits, and crossing local midnight?

## Blocked by

- None

## Progress

[FreshBooks live timer characterization](../../docs/research/live-timer-characterization.md) records the sanitized, cleaned-up observations for timer segmentation, pause/resume state, Duration Correction, consolidation/rounding on log, stale writes, and public Time Entry endpoint limitations. The web UI's two-request timer start shape is now captured: a blank unlogged Time Entry POST with `timer: {}` creates the timer identity, then a PUT assigns the selected project, service, identity, and note. Pause is a PUT that closes the open segment by replacing its null duration with elapsed whole seconds, without an explicit running flag. Resume POSTs a new open segment carrying the same timer identity and project/service metadata. A running Duration Correction PUTs every segment, preserving closed durations while rebasing the open segment to the requested aggregate. Remaining work is the exact log request and controlled CLI validation.
